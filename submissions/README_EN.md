# Leaderboard submission repository

This directory holds community benchmark submissions. CI aggregates them into the leaderboard reference (`baseline.json`), which supplies the reference means used for scoring.

The directory is currently empty — nothing has been accepted yet, so the reference embedded in release binaries is empty too (`sample_count: 0`). Until samples accumulate, the composite score is only meaningful with a reference file you supply through `--score-baseline`.

## What a submission carries, and what it does not

A submission is **not a compressed report; it is a different artifact**. A `full` report runs to a few thousand lines and hundreds of KB, and contains the egress IP, hostname, reverse DNS and per-hop routes — fields that are useless to a leaderboard yet quite sufficient to identify one specific machine.

The fields are therefore a **whitelist, not a blocklist**: adding one requires an explicit code change, so nothing new leaks out merely because a report grew a field.

```json
{
  "schema": "ecs.submission/v1",
  "id": "ddecbbc0421f",
  "fingerprint_version": "v2",
  "host": {
    "vcpu": 16,
    "memory_gib": 30.69,
    "virtualization": "kvm",
    "cpu_model": "AMD Ryzen 7 PRO 4750U with Radeon Graphics",
    "arch": "amd64",
    "region": "jp-tokyo",
    "provider": "vultr"
  },
  "tool": {
    "ecs": "v0.6.15",
    "sysbench": "sysbench 1.0.20",
    "fio": "fio-3.39",
    "iperf3": "iperf 3.16"
  },
  "ran_at": "2026-08-13T07:54:51Z",
  "profile": "standard",
  "memory_backend": "stream",
  "metrics": {
    "cpu_single": 1234.56,
    "cpu_multi": 9876.54,
    "memory_triad": 12345.67,
    "disk_seq_read": 890.12,
    "bandwidth_download": 945.6
  },
  "note": "monthly run"
}
```

| Included | Why |
| --- | --- |
| `host.vcpu` / `memory_gib` | Determines which tier the machine belongs to |
| `host.cpu_model` / `arch` / `virtualization` | Makes identical models comparable |
| `host.provider` / `region` | Grouping only, and **self-reported** — inferring them from an IP would require the very IP-intelligence data this format avoids |
| `tool.*` | Changing ecs or a benchmark tool can change the measurement contract; a benchmark corpus without versions becomes unexplainable numbers within months |
| `metrics` | The raw measured values scoring needs, keyed to the score dimensions |

| Excluded | Why |
| --- | --- |
| Egress IP, hostname, reverse DNS | Identifies the machine and helps grouping not at all |
| ASN, precise geolocation | Same |
| Per-hop route paths, disk serial numbers | Same |
| Any probe verdict outside the four score dimensions | A leaderboard has no use for them |

`ecs submit` prints this boundary when it finishes: **submissions carry only host specs and benchmark values; egress IP, hostname, route paths and ASN are never included.**

## Producing a submission

Run the tests to obtain a JSON report, then export the submission:

```sh
ecs --profile full --output ./reports
ecs submit --input ./reports/ecs-report-20260813-075451.json \
  --provider vultr --region jp-tokyo --note "monthly run"
```

Or do both in one shot:

```sh
curl -fsSL https://raw.githubusercontent.com/CST-Cat/ecs/main/run.sh | sh -s -- \
  --submit --profile full --yes --provider vultr --region jp-tokyo
```

Without `--output` the file goes to `${TMPDIR:-/tmp}` under its automatic name; pointing `--output` at an existing directory names the file inside it; pointing it at a path that does not exist yet uses that path. **An existing file is never overwritten**, and symlinks are rejected outright.

All three self-reported fields are optional: `--provider` (up to 48 characters), `--region` (up to 32) and `--note` (up to 200). If the `system` module detected a cloud provider or region, those are filled in automatically, and explicit command-line values take precedence.

## Where files go

```
submissions/
├── 2026-08/
│   ├── ddecbbc0421f-vultr-jp-tokyo.json
│   └── 3f9a12c4e5b7-hetzner-de-fsn.json
├── 2026-09/
│   └── ...
└── baseline.json        ← generated by CI, do not hand-edit
```

Two hard requirements:

1. **Exactly one subdirectory deep.** CI only collects `submissions/*/*.json`; a file placed at the root of this directory or nested deeper is invisible to it. Grouping by month is the current convention.
2. **The filename must agree with the contents** — that is, the name `ecs submit` produced: `<id>[-<provider>][-<region>].json`. The `id` is derived from the contents, while `provider`/`region` come from the self-reported fields, lowercased and hyphenated. A mismatched name makes the directory listing misleading, so CI rejects it.

`baseline.json` is CI output rather than input; aggregation skips it automatically.

## Validation rules

CI checks every file with `go test ./internal/score/ -run TestSubmissionCorpus` (`ECS_SUBMISSION_DIR=submissions`). You can run the same checks locally before submitting:

```sh
go test ./internal/score/ -run TestSubmissionCorpus -v
ecs leaderboard --strict --output /tmp/check.json submissions
```

A submission must satisfy all of the following:

- `schema` is exactly `ecs.submission/v1`; `fingerprint_version` is either absent (legacy algorithm) or `v2`;
- the file is a **single JSON object** with no unknown fields and no trailing content, and is at most 256 KiB;
- `metrics` is non-empty, every key is a registered score metric, and every value is a positive finite number;
- `host.vcpu` and `host.memory_gib` are positive; `tool.ecs` is non-empty; `note` is at most 200 characters;
- `memory_backend` is `stream` when STREAM memory metrics are present, and absent when they are not;
- **`id` matches the fingerprint recomputed from the contents**;
- the record does not duplicate one already in the repository (compared by canonical fingerprint).

Those last two matter most: the fingerprint is derived from the contents, so **editing a value without recomputing it is caught immediately**. By the same mechanism, changing `provider`, `region`, `note` or a tool version changes the `id`, which means the filename has to change with it — the correct fix is to re-run `ecs submit`, not to edit an existing file.

## Outlier detection

Aggregation flags outliers and surfaces them as GitHub Actions annotations on the check page:

```sh
ecs leaderboard --annotate --verbose --output /tmp/baseline.json submissions
```

**Outliers are advisory and never block a merge.** A machine far ahead of its tier may be new hardware, an unusual configuration, or bad data — that judgement belongs to a person, not to a threshold. `--verbose` additionally lists the combinations left unjudged for lack of samples.

## How the reference is rebuilt

On a push to `main`, CI:

1. re-aggregates with `ecs baseline --source "社区提交聚合" --output submissions/baseline.json submissions`;
2. copies the result to `internal/score/embedded/baseline.json` so release binaries embed the current reference;
3. builds and runs the scoring tests;
4. commits only if something changed.

The validation job is read-only. Write permission is granted to this one job and only on a push to the main branch, so the checks never modify the working tree and pull requests never run with write access.

## How the reference should be read

- Reference values are selected **by vCPU tier**: a multi-threaded score scales almost linearly with core count, so a single global mean would leave small machines permanently failing and large ones permanently maxed. A tier with too few samples falls back to the global mean and the report states which one was used.
- A **ranking** appears only when the reference file actually stores a score distribution and the sample count reaches the threshold (currently 5). A percentile is never derived from a host count.
- The sample count behind every metric is printed during aggregation. A metric measured by only one or two machines is far less representative than the rest, and users deserve to see that.

## Deliberate non-goals

Nothing is uploaded, downloaded, or merged from a remote baseline. Where the samples came from and what they represent stays in the hands of whoever uses them — which is the precondition for a score being explainable at all.
